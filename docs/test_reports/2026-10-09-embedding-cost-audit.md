另一个独立问题：数据库三张 daily-log 表的主键已为 `(app_id, project_id, id)`，运行旧代码的 `upsert` 默认冲突键仍为 `id`。使用排除 generated column 的 `EXPLAIN INSERT ... ON CONFLICT (id)`（只规划，未执行 INSERT）得到 `InvalidColumnReference` / SQLSTATE `42P10`；改为三个主键字段的规划通过。旧路径先调用 embedding，再 upsert；在账户恢复且有新增/变更时，存在先花 token 再写入失败的风险，旧 scanner 又可能重试。该风险已通过 SQL 规划证实，但没有实际付费执行来测金额。

## 缓解顺序与验收条件

1. **持久修复部署回退。** 从包含修复的完整源代码构建固定镜像，记录代码 commit / 镜像 digest；用该镜像部署。不要继续依靠只写在容器可写层的补丁。核对实际导入路径、无上限的 `find_entry_state`、三个字段的 upsert 键、失败任务不因 mtime 未变而自动重排、embedding 失败可写 NULL 并有 cooldown。
2. **先确认修复有效，再处理欠费和 backlog。** 旧服务恢复额度后仍有先 embedding 后 DB 失败的风险。修复后的 backlog 回填应手动、分批、明确 token 预算；不要无界全库重建或自动周期回填。
3. **把费用和行为纳入验收。** 对上述两份真实大文件做无变更重处理，断言 0 次 provider 调用；失败状态不发生 30 秒自循环。更重要的是创建一个全新容器再重复这些检查，验证补丁没有丢失。随后观察至少 24 小时账单与 provider `usage`。
4. **新增可归因指标与预算保护。** 记录成功请求的 `usage.total_tokens`、模型、任务原因（索引/查询/聚类/回填）、scope、文本 hash、md_path、输入数量和成功落库数；只记元数据，避免记录记忆正文。建议先以 200 万 tokens/日（当前价格约 1 元/日）作为预算保护的讨论起点，达到阈值后让索引进入等待、检索降级为关键词。该功能当前不存在，本次未实施；阈值应按恢复后的真实用量调整。仅做告警不能成为硬预算限制。
5. **再做次级优化。** 持久化内容 embedding 缓存可降低重试和同内容重复调用费用，缓存键须包含模型/端点/维度/文本 hash；重复 query 可短期缓存。允许延迟的回填可用官方异步 Batch API 半价。单纯调小并发或调大普通 `batch_size` 不会消除重复 token 费用；减小向量维度也不直接减少这项输入 token 账单。更换模型需要处理已有向量兼容性，先修循环再评估。
